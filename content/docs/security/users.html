Users

User Entity

Users of a Jmix application are defined by the User class that is automatically generated by Studio in a new project. It is a JPA entity implementing the JmixUserDetails interface which has a number of methods required by the framework:

  • getUsername() returns a unique user name.

  • getPassword() returns a hashed password.

  • isEnabled(), isAccountNonExpired(), isAccountNonLocked(), isCredentialsNonExpired() indicate whether the user can log in to the system.

  • getAuthorities(), setAuthorities() are used by the framework to associate the user with a set of permissions upon login.

Users are stored in the main database of your application. By default, the User entity and the corresponding database table have the following attributes:

  • id, version are the standard primary key and optimistic locking attributes.

  • username, password, enabled store values returned by the methods of the JmixUserDetails interface.

  • email, firstName, lastName store additional information about users.

You can define any number of additional attributes required for your application, for example, department or position.

Role Assignment Entity

A role assignment associates a user with a resource role or a row-level role.

In the standard database-backed implementation, role assignments are stored in the SEC_ROLE_ASSIGNMENT table as RoleAssignmentEntity instances. The entity has the following application-level attributes:

username

The value returned by the user’s UserDetails.getUsername() method.

roleCode

The code of a design-time or runtime role.

roleType

The type of the role. Use RoleAssignmentRoleType.RESOURCE for a resource role and RoleAssignmentRoleType.ROW_LEVEL for a row-level role.

The entity also contains standard identifier, version, audit, and soft deletion attributes.

See the User Registration sample project for a complete self-registration flow that creates a user and assigns the ui-minimal role using RoleAssignmentEntity.

User Management

A new project contains the 010-init-user.xml database migration script that creates a user with the admin/admin username/password and grants the user full access to the application by associating the user with the system-full-access role.

A new project also contains the UI views for managing users, see Application → Users. These views allow you to create, edit and remove users, change and reset their passwords. To assign roles to a user, click the Role assignments button in the user list view.

The new application project contains the ui-minimal role that gives permissions to log in to UI and to open the main view. Assign this role to new users that will interact with the application through the UI, otherwise they won’t be able to log in.

Password Change at Next Login

Jmix can require a user to change their password immediately after login. This behavior is controlled by a Boolean attribute of the User entity annotated with @PasswordChangeRequired.

@PasswordChangeRequired
@Column(name = "PASSWORD_CHANGE_REQUIRED")
private Boolean passwordChangeRequired = false;

If the authenticated user’s attribute annotated with @PasswordChangeRequired is set to true, Jmix opens the standard change password dialog in forced mode after login. In this mode, the user cannot close the dialog without saving a new password.

Use this mechanism in the following cases:

  • Set the annotated attribute to true for newly created users if they must change the initial password at the first login.

  • Use the Reset Password action with the Require change at next logon option to generate a temporary password and force the user to change it after login.

After the user successfully changes the password, Jmix automatically resets the annotated attribute to false.

Built-in Users

Any Jmix application with the standard security subsystem has two built-in user objects:

  • Anonymous user object corresponds to unauthenticated users and limits them to the login view. By customizing this object, you can grant some permissions to users before they log in.

  • System user object is required for the system authentication mechanism. It is used when there is no real user interacting with the application, for example, when the application is starting up, or when a business method is called by a scheduler.

The built-in user objects are not stored in the database but created on the application startup by the DatabaseUserRepository class of your project. You can customize both users in the initAnonymousUser() and initSystemUser() methods of this class.

DatabaseUserRepository.java
@Override
protected void initSystemUser(final User systemUser) {
    final Collection<GrantedAuthority> authorities = getGrantedAuthoritiesBuilder()
            .addResourceRole(FullAccessRole.CODE) (1)
            .build();
    systemUser.setAuthorities(authorities);
}

@Override
protected void initAnonymousUser(final User anonymousUser) { (2)
}
1 By default, the system user is granted the system-full-access role and hence has all permissions.
2 The anonymous user is not granted any role and hence has no permissions.
To simplify providing anonymous access to specific views, use @AnonymousAllowed.

User Substitution

The system administrator can give a user the ability to substitute another user. The substitution means the user has the resource and row-level roles of the substituted user. For example, if Alice substitutes Bob, she logs in to the application as Alice but has Bob’s roles.

To see the feature in action, do the following:

  1. Log in as admin and create at least one more user with the UI: minimal access role.

  2. Select admin in the Users table and click Additional → User substitution. You will see a list of users that admin can substitute.

  3. Create a new record with the user who admin should be able to substitute, then click OK in the list view.

  4. If your project’s main view includes the userMenu component with the sec_userMenuSubstituteUser action, the component’s dropdown will show a menu item with the substituted user.

  5. If your project’s main view includes the userIndicator component, the current user’s name will change to a dropdown list that contains the substituted user.

  6. When you select a substituted user in userMenu or userIndicator, the workspace will change as if you log in again as this user. But all audit features will still register admin (the logged-in user).

The CurrentUserSubstitution bean can be used to obtain a currently substituted user, an authenticated user, or the effective user (which is the substituted user in case of substitution, and the authenticated user otherwise).

For example:

@Autowired
private CurrentUserSubstitution currentUserSubstitution;

private String getSubstitutedUserName() {
    User substitutedUser = (User) currentUserSubstitution.getSubstitutedUser();
    return substitutedUser == null ? "" : substitutedUser.getUsername();
}

  • The CurrentAuthentication.getUser() method always returns the authenticated user.

  • The CurrentAuthentication.getAuthentication().getAuthorities() returns authorities of the effective user. That is, in the case of substitution, these authorities differ from the authorities of the authenticated user.

User Substitution Event

To track user substitution in application code, listen for io.jmix.core.security.event.UserSubstitutedEvent. It is published after the new substituted authentication is installed in the current security context.

    @EventListener
    public void onUserSubstituted(UserSubstitutedEvent event) {
        UserDetails authenticatedUser = event.getAuthenticatedUser();
        UserDetails substitutedUser = event.getSubstitutedUser();
        log.info("User substituted: " + authenticatedUser.getUsername()
                + " -> " + substitutedUser.getUsername());
    }
